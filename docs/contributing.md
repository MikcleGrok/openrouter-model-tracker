# Contributing: как изменение доходит до master

Изменение в этом репозитории проходит один и тот же путь: отдельная ветка на
одну задачу, pull request с историей вместо голого списка коммитов, гейты —
реальные `make`-таргеты, а не пересказ намерений, — и ревью там, где решение
несёт суждение, а не просто повторяет уже принятое. Этот документ описывает
именно эту, уже сложившуюся практику: не придуманный заново процесс, а то, как
устроены 46+ смерженных PR этого репозитория сегодня, и то, как с этого
момента должно выглядеть описание PR — с историей в начале, а не только
буллетами.

## Кратко

- **Ветка** — одна задача, один branch, kebab-case имя (`windows-release-target`,
  `cosign-key-rotation`) или `release-v<version>` для релизных веток; коммиты —
  `type(scope): subject` (`feat`, `fix`, `docs`, `test`, `refactor`, `perf`,
  `security`). → [Именование веток и коммитов](#именование-веток-и-коммитов)
- **PR** — открывается через `gh`; описание начинается с короткой истории (что и
  зачем), затем `## Summary` и `## Verification` с реально выполненными
  командами. → [Описание PR](#описание-pr)
- **Гейты** — `make`-таргеты (`fmt-check`, `test`, `check-docs`, `security`, …)
  прогоняются до merge, их вывод — не голословное заявление, а доказательство в
  Verification. → [Гейты перед merge](#гейты-перед-merge)
- **Ревью** — не для каждого PR обязательно, но для решений с суждением —
  отдельный проход, который ищет то, что гейты не поймают. → [Ревью](#ревью)
- **Merge** — настоящий merge commit с двумя родителями, историю ветки не
  squash'ят. → [Слияние](#слияние)
- **Дальше** — тег, релиз и подпись — отдельный, уже задокументированный
  процесс. → [Что дальше](#что-дальше)

## Именование веток и коммитов

Одна ветка — одна логическая единица работы, имя — kebab-case, по смыслу
задачи: `windows-release-target`, `fix-missing-snapshot-and-completion`,
`cosign-key-rotation`. Ветки, готовящие релиз, называются `release-v<version>`.

Тема коммита — `type(scope): subject`, в духе Conventional Commits, но без
формального enforcement. Типы, которые реально встречаются в истории
репозитория: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `security`.
Scope — необязателен, но обычно называет подсистему, а не файл; в одном
коммите их может быть несколько через запятую. Примеры из реальной истории:

- `feat(release): add windows/amd64 release target`
- `fix(release,readme): align Windows preflight check with packaging logic`
- `docs(readme): rework demo GIF to show Claude, filter, and help screen`
- `security(cosign): rotate the release-signing key pair`

Subject — императив, короткий, без точки в конце. Детали, которые не
поместились в один заголовок, идут в тело конкретного коммита, если относятся
только к нему, а не ко всему PR — для этого уровня и существует `## Summary`
в описании PR.

## Описание PR

PR открывается через `gh pr create` (или веб-интерфейс GitHub) — шаблона
`.github/pull_request_template.md` в репозитории нет, есть только
наблюдаемая практика по 46+ смерженным PR. Сегодня эта практика — голые
буллеты `## Summary` без единого слова вступления: что изменилось,
перечислено, но не рассказано, зачем. Дальше это не так: описание PR
открывается короткой историей — какая проблема стояла, почему она важна, в
какой форме получилось решение, — и только после неё идут `## Summary` и
`## Verification`. Одного-двух абзацев достаточно: PR читает не только
автор, а история экономит рецензенту минуты на реконструкцию контекста,
которые иначе тратятся на чтение diff в поисках «зачем».

Форма (пример, не цитата конкретного PR):

```markdown
Windows-сборка существовала только в теории: release matrix собирала
бинарники только для macOS и Linux, а пользовательский запрос на .exe
годами оставался без ответа. Этот PR добавляет windows/amd64 в release
target, preflight-проверку и упаковку в zip — тем же циклом curl →
распаковка → binary, что уже работает для остальных платформ.

## Summary
- Добавлен `windows/amd64` в список release-платформ и preflight-проверка `zip`/`unzip`.
- Windows-архив собирается как `.zip` с единственным `.exe` внутри вместо `tar.gz`.
- README дополнен инструкцией для Windows и предупреждением про SmartScreen.

## Verification
- `make fmt-check`
- `make test`
- `make check-docs`
- `make release-local`
```

`## Summary` — 1-3 буллета, что изменилось и зачем, без дословного повтора
истории выше. `## Verification` — не абстрактное «протестировано», а список
реально выполненных команд и, если нужно, конкретных fixture-тестов; например,
PR #45 добавил в этот раздел ручную jq-репродукцию бага (`Cannot index array
with string ("artifacts")` — до фикса, и то же выражение проходит после) — это
тот уровень конкретности, к которому стоит стремиться, а не «все тесты
прошли».

## Гейты перед merge

Перед merge прогоняются `make`-таргеты — те же, что видно в Verification
выше: `fmt-check`, `test`, `check-docs`, `security`, `sign-flags-check`,
`provenance-profile-check` и другие, в зависимости от того, что затронул PR.
Полный и всегда актуальный список — в [reference.md](reference.md#makefile)
(раздел Makefile) и в самом `make help`; этот документ его не дублирует,
потому что дублирующийся список гарантированно разойдётся с реальным
Makefile.

Гейт — это не факт запуска, а evidence: команда и её результат, зафиксированные
в `## Verification` PR. Голословное «tests pass» без списка команд не
покрывает конвенцию — рецензент должен суметь повторить тот же запуск и
получить тот же результат.

## Ревью

Ревью не гейтится инструментом — оно происходит там, где изменение несёт
суждение, а не механически повторяет уже принятое решение: новая логика, а не
опциональный флаг; пересечение нескольких подсистем; всё, что тяжело
откатить post-merge. Для чисто механических правок (опечатка в README,
патч-версия зависимости) отдельного ревью может не быть — гейты уже
покрывают правильность.

Конкретный пример из истории репозитория (2026-09-12, ветка
`windows-release-target`): изменение `Makefile`, добавляющее Windows release
target, прошло независимый adversarial-review перед merge — и он нашёл два
реальных дефекта, которые тестами не ловятся:

- в README не было предупреждения про SmartScreen для неподписанного `.exe`
  — пользователь получил бы пугающее системное предупреждение без
  объяснения, что оно ожидаемо;
- preflight-проверка наличия `zip`/`unzip` сравнивала с сырой строкой
  `platform`, а сама логика упаковки — с производной переменной `$os`; при
  некорректном override платформы эти два пути могли разойтись, и preflight
  пропустил бы сборку, которая на самом деле упадёт при упаковке.

Оба дефекта были исправлены до merge, одним коммитом `fix(release,readme):
align Windows preflight check with packaging logic` (`18d3990`), и только
после этого ветка попала в master. Ни один из двух дефектов не всплыл бы на
`make test` — оба про то, что код делает не то, что подразумевал автор, а не
про то, что он не компилируется или падает на существующих кейсах. Это и
есть работа ревью: искать несовпадение подразумеваемого и написанного там,
где гейт может быть зелёным, а логика — всё равно неверной.

## Слияние

PR мержится настоящим merge commit — с двумя родителями, не squash.
`git log --merges` показывает это буквально: у каждого merge-коммита в
истории по два parent-хэша после хэша самого коммита. Ветка не переписывается
и не схлопывается в один коммит — все промежуточные коммиты остаются видны в
`git log` после merge, со своими типами и сообщениями, так что `git
blame`/`git bisect` после merge всё ещё видят историю по шагам, а не один
большой diff.

## Что дальше

Слияние в master — не конец процесса, а его середина: дальше идёт
тегирование и релиз, полностью описанные в [reference.md](reference.md)
(раздел про release-процесс: `make release-check`, `make release-local`,
`make whats-new`), и подписывание артефактов — в [security.md](security.md)
(cosign-ключ, provenance). Этот документ их не повторяет: раздел про merge
заканчивается на самом merge, а не на том, что случается с тегом потом.
